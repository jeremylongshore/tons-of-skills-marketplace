# Freshie — Ecosystem Inventory & Compliance System

Configuration Management Database (CMDB) for the claude-code-plugins ecosystem.
Every plugin, skill, agent, command, and file in the repository, scanned into
versioned "discovery runs" with validator grades on top.

**The versioned history is public:**
<https://www.dolthub.com/repositories/jeremylongshore/freshie-inventory>
(live since 2026-07-11 — browse tables in the web UI, query without cloning,
`dolt clone jeremylongshore/freshie-inventory` for the whole thing).

## The hybrid storage model

| Artifact | Role | Tracked? |
|---|---|---|
| `freshie/inventory.sqlite` | **Local runtime format.** Every tool reads/writes this — the validator's `--populate-db`, `rebuild-inventory.py`, the JRig proof recorder (`scripts/record-jrig-proofs.mjs`), ad-hoc `sqlite3` queries. | No (untracked since 2026-07; the blob used to be ~all of `.git`) |
| `freshie/dolt/freshie/` | **Local Dolt repo — the versioned system of record.** One commit + one `run-N` tag per inventory run, pushed to DoltHub. | No (gitignored) |
| DoltHub `jeremylongshore/freshie-inventory` | The public, durable copy of the Dolt history. | — |
| `freshie/grades.csv` + `freshie/grade-histogram.json` | **Tracked compact export**, regenerated by every sync. One row per skill in the **current run** (`skill_path,grade,score` — deliberately no per-row run_id, so the git diff shows only real grade movement; a skill deleted from the repo drops out instead of ghosting on its last grade). The histogram carries the run_id the rows came from, plus `dolt_commit` — the immutable Dolt revision the export was cut from (stamped post-commit by the sync). | Yes |
| `freshie/disposition-ledger.json` | **Tracked Blueprint 727 §8 projection.** One first-match-wins disposition per current Freshie-graded artifact. It records only machine facts and keeps clean artifacts at `CERTIFY-PENDING-EVIDENCE` until retained evidence exists. | Yes |
| `freshie/reports/run-delta-<N>.json` | **Per-run delta report**, emitted post-commit by every sync (regenerable any time via `run-delta.py`). Schema-vs-data change classification per table + run-over-run grade regressions + the Dolt commit hash. See "Run-delta & regression signal" below. | Yes |
| `freshie/doltlite/freshie-inventory.db` | **Native DoltLite shadow history.** A local sidecar used to prove SQLite-compatible branch, diff, merge, rebase, clone, and push behavior without changing Freshie's stock-SQLite runtime. | No (gitignored) |
| `freshie/doltlite-schema-baseline.json` | Reviewed public schema/column allowlist for the DoltLite lane. Drift fails before target mutation unless an operator explicitly regenerates this tracked review artifact. | Yes |
| `freshie/reports/source-snapshot-run-<N>.json` | Required human-reviewed source authorization. Its immutable seal binds the named SQLite backup SHA, exact full-Dolt commit/database hash/direct parent, schema baseline, and every table receipt. It must be committed and clean at `HEAD` before the publisher will open the target. | Yes |
| `freshie/reports/doltlite-run-<N>.json` | Immutable content, schema, engine, source-backup SHA, verified full-Dolt predecessor, DoltLite commit, required-ref, and run-parent receipt. Publication progress is kept separately in the recoverable `.publication.json` journal. | Yes |

> **Local is the sole writer.** Never merge DoltHub PRs, never web-edit the
> public database, never hand-edit `freshie/dolt/`. The exporter is strictly
> one-way (SQLite → Dolt) and never force-pushes: a commit made on the
> DoltHub side makes the next sync's push fail non-fast-forward (loud, exit
> 3) and the pipeline stays stuck until an operator resolves it. Recovery:
> verify local is authoritative (it always is — the remote edit was against
> the rules), then from `freshie/dolt/freshie` run
> `dolt push --force origin main` and re-run the sync.
>
> **Push ≠ backup.** The DoltHub push is what makes history durable and
> publicly visible; borg on the VPS is backup. Until a sync pushes, Dolt
> history is single-copy on this box — which is why `dolt-sync.py` exits
> non-zero and loud when a push fails.

## The inventory cycle

```bash
# 1. Discovery scan (creates run_id = N+1)
python3 freshie/scripts/rebuild-inventory.py

# 2. Compliance validation (fills skill/agent/plugin_compliance for the run)
python3 scripts/validate-skills-schema.py --marketplace --populate-db freshie/inventory.sqlite

# 3. Sync to the system of record: Dolt commit, run-N tag, DoltHub push
python3 freshie/scripts/dolt-sync.py

# Read-only freshness check for the tracked export pair. This refuses a
# histogram run stamp or CSV row count that no longer matches the latest DB run.
python3 freshie/scripts/dolt-sync.py --verify-grade-exports

# 4. Refresh the skills.sh discovery mirror from the new grades (optional; also
#    runs weekly via .github/workflows/promote-curated.yml).
python3 freshie/scripts/promote-to-curated.py

# 5. Commit the refreshed grades.csv / grade-histogram.json (and skills/.curated/)
#    with your PR.

# 6. Regenerate the fail-closed disposition ledger from the refreshed graded cohort.
pnpm run generate:disposition-ledger
```

## The skills.sh curated mirror (`promote-to-curated.py`)

skills.sh only crawls a repo's root `skills/` (+ `.curated/`, `.experimental/`, agent
dirs) — it does **not** descend into `plugins/**/skills/`, where ~3,100 of our skills
live. `promote-to-curated.py` bridges that: it rebuilds `skills/.curated/` as a generated
**mirror** of our best plugin skills so skills.sh can index them.

- **Selection:** grade **A + B**, plugin skills only, our own (a plugin root carrying a
  `.source.json` external marker is excluded), source dir present → ~1,881 skills. Read
  from the **tracked** `grades.csv` (not the git-ignored `inventory.sqlite`) so the CI
  drift gate is reproducible in a clean checkout.
- **Source of truth stays the plugin skill.** The copies under `skills/.curated/` are
  rebuilt every run (wipe-and-rebuild) and never hand-edited; only git-tracked source
  files are copied, so a local build == a CI build.
- **Defense:** each candidate is re-graded in-process by the canonical validator; it is
  promoted only if its fresh grade is still A/B (drops a source that regressed since the
  last run). Gated on the grade, not the non-blocking marketplace error list.
- **Audit trail:** `skills/.curated/MANIFEST.json` records every promoted skill (source
  path, recorded + fresh grade, run_id).
- **Honest counts:** `skills/.curated/` is excluded from the README skill count
  (`generate-readme-toc.mjs`) and from the Freshie inventory scan
  (`validate-skills-schema.py` `find_skill_files`), so a mirror copy is never
  double-counted.

```bash
python3 freshie/scripts/promote-to-curated.py            # rebuild skills/.curated/
python3 freshie/scripts/promote-to-curated.py --check    # CI drift gate (exit 1 if stale)
python3 freshie/scripts/promote-to-curated.py --no-validate   # skip the in-process re-grade
```

**Self-maintenance:** `.github/workflows/promote-curated.yml` rebuilds the mirror weekly
and opens a PR on change (never a blind push); the `promote-curated-check` job in
`validate-plugins.yml` fails any PR that edits a promoted source without regenerating the
mirror. Repo-page branding for skills.sh lives in root `skills.sh.json`.

Both scripts derive the repo root from their own location — they are safe to
run from a git worktree (proven: run 9 was executed entirely from one).

Other operations:

```bash
python3 freshie/scripts/rebuild-inventory.py --export    # CSV export per run
python3 freshie/scripts/rebuild-inventory.py --diff      # compare runs
python3 freshie/scripts/rebuild-inventory.py --dry-run   # scan preview
python3 freshie/scripts/dolt-sync.py --dry-run           # show translated DDL + plan
python3 freshie/scripts/dolt-sync.py --no-push           # local sync only
python3 freshie/scripts/dolt-sync.py --recreate-tables   # after a legit schema change
python3 freshie/scripts/dolt-sync.py --alert-on-regression  # exit 4 when grades regressed
python3 freshie/scripts/run-delta.py                     # (re)generate the newest run's delta report
python3 -m unittest tests.test_dolt_sync tests.test_run_delta -v  # exporter + delta unit tests (71)
```

## Native DoltLite shadow publisher

Freshie is a legitimate DoltLite use case, with an important rollout boundary:
the live CMDB remains stock SQLite and the existing
`jeremylongshore/freshie-inventory` repository remains the full-Dolt archive.
The shadow publisher creates a **native DoltLite** sidecar from one consistent
SQLite snapshot, runs the canonical incomplete-run, retained-evidence, and
tracked-grade gates, proves every approved table's row multiset and logical
schema contract, commits it, and assigns an immutable `run-N` branch. A
process-wide lock protects the multi-autocommit copy. DoltLite run branches
replace tags because DoltLite tags are currently local-only when pushing.

The DoltHub target must be a separate repository named
`jeremylongshore/freshie-inventory-doltlite`. DoltHub fixes a repository's
database engine on its first push, so the established full-Dolt repository
cannot also accept a DoltLite database. The old repository is retained as the
lineage source and rollback path; it is not rewritten.

```bash
# Requires the sqlite3 CLI and a Python whose sqlite3 extension is dynamically
# linked (system/Homebrew/pyenv/Conda Python; not python-build-standalone).
python3 -m venv .venv-doltlite
.venv-doltlite/bin/pip install -r freshie/requirements-doltlite.txt

# Migration root: use a reviewed stock-SQLite run-19 snapshot in a new sidecar.
# This is the only ancestry bootstrap accepted by the publisher. Publication
# intentionally remains blocked until this receipt exists in a reviewed commit.
.venv-doltlite/bin/python freshie/scripts/doltlite-sync.py \
  --db <reviewed-run-19-inventory.sqlite> \
  --source-receipt freshie/reports/source-snapshot-run-19.json \
  --bootstrap-run-19

# Then sync run 20. The publisher requires main/run-20 to descend from run-19.
.venv-doltlite/bin/python freshie/scripts/doltlite-sync.py

# Public shadow publication. Never accepts a caller-supplied predecessor:
# it resolves and cross-checks the public full-Dolt run-N tag itself.
.venv-doltlite/bin/python freshie/scripts/doltlite-sync.py --push
```

The checked-in `doltlite-schema-baseline.json` is the **exact 41-table DoltLite
publication denominator**, not merely an upper-bound allowlist. It records the
ten canonical-export tables deliberately excluded from this shadow:
`npm_discovery_runs`, `npm_dist_tags`, `npm_download_stats`, `npm_fetch_log`,
`npm_package_dependencies`, `npm_packages`, `npm_publish_history_summary`,
`npm_version_comparisons`, `npm_versions`, and `repo_package_sources`. The same
artifact is the column-level public-data review plus a logical schema-contract
hash. A new or missing table fails until the denominator itself is separately
reviewed and changed; `--approve-schema-drift` cannot silently widen it. A
column, index, foreign key, hidden/generated column, or type/nullability change
also fails before the DoltLite file is opened. After reviewing that schema
exposure, regenerate the contracts explicitly with `--approve-schema-drift`
and commit the baseline with the schema change.
Views and triggers remain unsupported and fail closed rather than disappearing.
High-confidence private-key and provider-token shapes are scanned across every
approved table before target mutation; failures identify only table, column, and
row position and never print the candidate secret.

The lineage resolver independently established public full-Dolt run 19 as
commit `vdc8inn59b1n0oor6m5hfjesbvnc2nl9`, database hash
`ue4mdhgoolqfjb5juasqb97ufrechk96`, and direct parent
`8ih5losgj9120patrkdulsml0gtn9clj`; it re-resolves these values from DoltHub at
execution time rather than trusting this documentation. The required per-run
source receipt must bind that exact evidence, the consistent SQLite backup SHA,
and the hash of all 41 table receipts. A missing, modified, uncommitted, or
resealed-but-mismatched receipt stops before target creation.

Before the first public push, create the empty DoltLite-typed DoltHub repository
and register the public key returned by `SELECT dolt_creds_new()` in DoltHub.
DoltLite credentials are separate from the legacy `dolt login` credentials.
Before any push the publisher writes the immutable run receipt and a separate
publication journal. For run N>1 it idempotently pushes the immutable
predecessor, then `run-N`, then `main`, recording each transition; the remote
operations are deliberately not described as atomic. A failure leaves journal
state `failed`, `partial`, or
`pushed-unverified`; rerun the same `--push` command to resume without rewriting
history. Only a clean clone whose predecessor, `main`, and `run-N` hashes match
the receipt and whose `run-N` direct parent is that predecessor can advance the
journal to `complete`. A non-fast-forward push, unknown source
table, parity mismatch, schema mismatch, receipt change, stale canonical export,
unretained evidence claim, or attempt to repoint a run branch fails closed.

Runtime rollback is deletion of an **unpublished** untracked
`freshie/doltlite/` sidecar and continued operation against stock
`freshie/inventory.sqlite`; the runtime and full-Dolt archive are untouched.
After either remote ref has been pushed, do not delete the sidecar or journal:
resume publication or diagnose the recorded partial state. Public Dolt history
is immutable and is never rolled back with force-push or history rewriting.

## Querying

**Runtime (local SQLite)** — unchanged, zero migration for consumers:

```bash
sqlite3 freshie/inventory.sqlite "SELECT grade, COUNT(*) FROM skill_compliance WHERE run_id = 9 GROUP BY grade;"
```

**History (Dolt)** — the run_id model is append-only, so `dolt diff` between
run tags shows *added rows*, not cell changes. History questions are asked
with `WHERE run_id = N` or `AS OF`:

```bash
cd freshie/dolt/freshie

dolt sql -q "SELECT grade, COUNT(*) FROM skill_compliance AS OF 'run-9' WHERE run_id = 9 GROUP BY grade;"
dolt diff run-8 run-9 --stat        # what run 9 appended, table by table
dolt log --oneline                  # one commit per sync
```

For the human-readable "skill X went B→A" story, use git instead:
`git log -p freshie/grades.csv`.

**Clone-free (DoltHub SQL API)** — query the public record from anywhere:

```bash
curl -s "https://www.dolthub.com/api/v1alpha1/jeremylongshore/freshie-inventory/main?q=SELECT+COUNT(*)+FROM+skill_compliance"
curl -s "https://www.dolthub.com/api/v1alpha1/jeremylongshore/freshie-inventory/main?q=SELECT+tag_name+FROM+dolt_tags"
```

## Run-delta & regression signal

After each sync commits run N, a **non-fatal post-commit step** (same
loud-skip discipline as gc — a delta failure never fails a sync that already
committed) writes `freshie/reports/run-delta-<N>.json` and prints a one-line
summary a GitHub-Actions step can consume:

```
[dolt-sync] run-delta: run-8 → run-9 · 12 tables changed (2 schema) · +3783/-0/~0 rows · 5 grade regressions → freshie/reports/run-delta-9.json
```

The report answers two questions the append-only model couldn't before:

- **Did the SHAPE change, or just the content?** Per-table
  `DOLT_DIFF_SUMMARY` / `DOLT_DIFF_STAT` between the two run tags — a
  `schema_change: true` flag distinguishes a `--recreate-tables` schema
  migration from routine appended rows (e.g. `run-delta-9.json` shows the
  run-9 → run-9.1 repopulation carried **7 schema changes**, invisible in
  `git diff grades.csv`).
- **Which skills got WORSE?** `grade_regressions` lists every skill whose
  grade dropped between the two tags (A→B etc.), computed from a temporal
  `AS OF '<tag>'` compare of `skill_compliance` at the two tagged revisions —
  a data-quality probe emitted as structured output. The compare is
  **tag-over-tag** (adjacent tags in `(run, suffix)` order), so an intra-run
  repopulation pair like run-9 → run-9.1 is compared too, not only full
  run-over-run movement.

Every report (and `grade-histogram.json`) also carries `dolt_commit` — the
immutable Dolt revision the artifact was cut from, so exports trace to
exact history, not just a tag name.

Default is **inert**: the report is written, nothing else fires. Opt-in
signal for CI/automation: `--alert-on-regression` (on `dolt-sync.py` or
standalone `run-delta.py`) exits **4** when regressions were found — the
sync itself still succeeded; downstream decides what to do. Regenerate any
run's report without syncing:

```bash
python3 freshie/scripts/run-delta.py                  # newest run
python3 freshie/scripts/run-delta.py --run-id 9       # specific run
```

## Restore path (battle-tested)

> This is not theoretical: on 2026-07-10 a branch switch destroyed the live
> `inventory.sqlite` hours after the first sync, and it was rebuilt from the
> Dolt record with zero data loss.

If `inventory.sqlite` is lost, rebuild it from Dolt:

1. **Get the data.** `dolt clone jeremylongshore/freshie-inventory` (or use
   the local `freshie/dolt/freshie/` if it survived).
2. **Rebuild the sqlite file.** Per table, read rows with
   `dolt sql -r json -q "SELECT * FROM <table>"` and INSERT them via Python's
   `sqlite3` with parameter binding. Use JSON, not CSV: the `sqlite3` CLI's
   `.import` reads an empty CSV field as `''`, silently destroying every NULL.
   JSON preserves NULL vs `''` exactly, and sqlite column affinity restores
   mixed-type columns on its own. Two fidelity touch-ups: recreate the schema
   from `reports/00-data-dictionary.md` (or a prior sqlite snapshot in
   `archives/`), and convert DATETIME text from `YYYY-MM-DD HH:MM:SS.ffffff`
   back to the original `T`-separated ISO form for the 5 declared-TIMESTAMP
   columns.
3. **Prove the restore.** Run `python3 freshie/scripts/dolt-sync.py --no-push`.
   If it reports `commit created: False` with all gates green, the restored
   DB is content-identical to the Dolt record — every NULL, empty string,
   float, and datetime round-tripped. Anything less and it will either fail a
   gate or create a diff commit; investigate before trusting the file.

## How the exporter works (dolt-sync.py)

- **Consistency + safety:** flock (`freshie/dolt/.sync.lock`), refusal while a
  `dolt sql-server` holds the repo, `VACUUM INTO` tmpfs snapshot so all 51
  table exports read one point in time, `reset --hard` + `clean` on entry to
  clear dead prior runs.
- **Export allowlist:** only the 51 intended CMDB tables (`EXPORT_ALLOWLIST`
  in `dolt-sync.py`) are published. The known j-rig runtime tables (`runs`,
  `run_summaries`, `skill_versions`, `criterion_results`, `artifacts`,
  `skill_usage_events`, `skill_human_reviews` — j-rig writes them into
  whatever `--db` it is handed) are excluded with a log line; any other
  unknown table is a **hard fail** (nothing unreviewed ever reaches the
  public record). Going-forward only: DoltHub runs ≤ 9.1 already carry the
  j-rig tables and history is never rewritten.
- **Schema translation:** INTEGER→BIGINT, REAL→DOUBLE, TIMESTAMP→DATETIME(6)
  (values carry microseconds), TEXT→LONGTEXT (TEXT primary keys → VARCHAR(255)
  with a max-length guard); AUTOINCREMENT stripped; every identifier
  backticked; BLOB is a hard fail. Columns whose *data* violates their
  declared type are widened to LONGTEXT with a loud log line — SQLite typing
  is advisory (real case: `agent_files.fm_max_turns`, an INTEGER column
  holding YAML-comment cruft).
- **Pump:** `sqlite3 -header -csv` → `dolt table import -r`. NULL vs `''`
  round-trips without a sentinel; a fixture canary re-proves the
  NULL/`''`/DATETIME(6)/quoting contract on every run, and on canary failure
  empty-string-bearing tables fall back to batched multi-row INSERTs.
- **Gates before commit:** per-table `COUNT(*)` parity, float-tolerant
  checksums on every REAL column, per-row MD5 byte checksums on the
  JSON-bearing TEXT columns. Any miss aborts before anything is committed.
- **Commit/tag/push:** `dolt commit --skip-empty`; the `run-N` tag is created
  only when it tells the truth (crash-retry and re-populate cases handled);
  the tag is pushed via explicit refspec — tags don't ride along on a branch
  push. Any older local tag missing from the remote (stranded by a prior
  failed push) is pushed too, so a failed run's tag heals on the next
  successful sync. Push failure = exit 3 with a classified diagnosis
  (repo-missing vs creds).
- **Idempotent by construction:** re-running against unchanged data converges
  — no duplicate commit, tag recognized at HEAD. This is also the restore
  verifier (above).
- **Hygiene:** `dolt gc` under the sync lock every 5 syncs or when the repo
  dir doubles. The live-server check re-runs immediately before `dolt gc`
  (a `dolt sql-server` started mid-sync takes no flock); if one appeared —
  or gc itself fails — the sync still exits 0, because commit+push already
  succeeded; gc stays due for the next run.

Pushing is operator-box-only: it requires DoltHub creds from `dolt login`
(a creds keypair on this machine). `dolt-sync.py` deliberately implements
no env-var/CI credential path (no `--user`/`DOLT_REMOTE_PASSWORD`) — local
is the sole writer and CI never pushes. Any environment that merely
creates commits still needs a commit identity
(`dolt config --global --add user.name/user.email`).

## Database design

**51 tables** organized in groups:

| Group | Tables | What |
|-------|--------|------|
| Core entities | packs, plugins, skills | The ecosystem topology |
| Metadata | frontmatter_*, plugin_* | YAML/JSON field analysis |
| File analysis | skill_files, content_signals, duplicates | Deep file scanning |
| Components | command_files, agent_files | Slash commands & agents |
| Compliance | skill/agent/plugin_compliance | Validator scores & grades |
| Infrastructure | scripts, validators, ci_workflows | Build system catalog |
| Dependencies | npm_* | npm registry intelligence |
| Documentation | docs | All .md files cataloged |

**Versioned runs:** every table has a `run_id` column — old data stays, new
data appends. Each sync tags the Dolt history `run-N`, so the same question
can be asked three ways: `WHERE run_id = N` (either engine), `AS OF 'run-N'`
(Dolt), or the git history of `grades.csv` (grade movement only).
