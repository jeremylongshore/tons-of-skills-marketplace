# Claude Mods and a Model-Neutral Marketplace: Captured Contracts, Trust Boundaries, and Validation Requirements

Engineering research record, October 22, 2026 (public capture window October 23 UTC). Record 821: `000-docs/821-RL-RSRC-claude-mods-impact.md`. Research bead: claude-e6e6. Repository baseline: d815a33ccd31ce5e272e0ebba8f94416c6b1a66e. Status: source-backed research recommendation, not an adoption decision.

## Abstract

Claude’s extension interface raises a compatibility question for a marketplace that separates portable skills from native extensions. This report compares the original Function Hooks proposal with captured Claude Mods documentation, release records, public source, and the marketplace’s pinned implementation. A bounded engineering review collected 25 substantive public artifacts and four provenance records, examined 20 repository entrypoints, and recorded 12 inert calls to an existing hooks-validation function. Independent source verification reproduced the capture identities and a 141-name textual event inventory. Release publication is corroborated, but public declarations lag the documented interface. Two current documentation statements conflict with published release changes. Local observations identify module-declaration, scanner-classification, and distribution seams without demonstrating a runtime exploit or complete admission failure. Documented broad authority, conditional guard enrollment, failure continuation, shared-worker recovery, and host-specific UI support prevent treating installation as enforcement certification. The report recommends continuing bounded design work while preserving portable/native separation. An explicitly approved isolated pilot could generate missing build-specific evidence. Production support and security claims would require successful tests and retained receipts. No native activation, provider operation, implementation bead, or policy change is authorized by this research.

**Keywords:** Claude Mods, extension compatibility, portable skills, middleware, trust boundaries, validation, source provenance.

## 1. Context and research question

The marketplace’s approved identity decision preserves one canonical portable skill tree and treats native extensions as a separate product class. Its harness registry records skill-discovery support, while its existing adapter projects model classes and runtime variables. Those artifacts do not establish translation of native event middleware. Consequently, a native extension can be relevant and useful without becoming a portable skill. [R03 000-docs/803-AT-ADEC-model-neutral-identity-migration.md](https://github.com/jeremylongshore/tons-of-skills-marketplace/blob/d815a33ccd31ce5e272e0ebba8f94416c6b1a66e/000-docs/803-AT-ADEC-model-neutral-identity-migration.md), [R04 config/harness-registry.json](https://github.com/jeremylongshore/tons-of-skills-marketplace/blob/d815a33ccd31ce5e272e0ebba8f94416c6b1a66e/config/harness-registry.json), [R16 scripts/adapters/claude-code-adapter.mjs](https://github.com/jeremylongshore/tons-of-skills-marketplace/blob/d815a33ccd31ce5e272e0ebba8f94416c6b1a66e/scripts/adapters/claude-code-adapter.mjs)

The original issue and its architecture PDF describe a function-based extension design. Current official sources identify a released product called Claude Mods, corroborated by the stable 2.1.287 release. The research therefore concerns compatibility with a published interface rather than a hypothetical feature. Publication still differs from verified behavior in this repository. [S01 Issue 91870 proposal and dated updates](https://github.com/anthropics/claude-code/issues/91870), [S02 Function Hooks Core Architecture attachment](https://github.com/user-attachments/files/31802150/EXTERNAL.Function.Hooks.Core.Architecture.pdf), [S03 Customize Claude Code with mods](https://claude.com/resources/articles/claude-code-mods), [S22 CLI v2.1.287 release metadata](https://github.com/anthropics/claude-code/releases/tag/v2.1.287)

The primary question is: **What compatibility constraints does a source-verifiable released Claude extension interface impose on this marketplace’s model-neutral extension boundary at explicitly captured versions?** Three subquestions guide the analysis: which contracts changed from proposal to release, which mappings preserve marketplace authority and security boundaries, and what evidence would justify a bounded recommendation without conferring adoption authority?

The intended readers are marketplace maintainers and reviewers considering future native integration. The report does not compare user productivity, benchmark competing runtimes, or estimate economic benefit. Those questions require different evidence.

### 4.4 Marketplace admission and distribution seams

Native packaging documentation distinguishes the plugin manifest from the hooks configuration carrying the module path. Published built-in source and the diff example provide concrete implementation context, but source publication does not bind every inspected byte to an installed binary. The guard registration entry imports policy dependencies outside the captured closure. Neither that entry nor the diff example ran in this study. ## 6. Recommendation and migration conditions

**Go for bounded design work and the source-backed brief.** The released interface and its relevance to middleware/UI/native integration are sufficiently corroborated to justify a separately reviewable proposal. The original architecture source was recovered, and documentary uncertainty is specific rather than total. [S02 Function Hooks Core Architecture attachment](https://github.com/user-attachments/files/31802150/EXTERNAL.Function.Hooks.Core.Architecture.pdf), [S03 Customize Claude Code with mods](https://claude.com/resources/articles/claude-code-mods), [S05 Mods reference](https://code.claude.com/docs/en/plugins/mods/reference), [S22 CLI v2.1.287 release metadata](https://github.com/anthropics/claude-code/releases/tag/v2.1.287)

**No-go for automatic adoption, current production qualification, or untested enforcement claims.** This is a recommendation about present evidence and authority. Native pilot activation remains unapproved. It is not a permanent rejection, and legacy admission behavior alone does not determine the architectural outcome.

A future decision could authorize a narrow isolated pilot after selecting exact host/build/generated declarations, reviewing trusted imports and authority, resolving or constraining disputed semantics, and approving bounded effects and rollback. Proposed validator/scanner/distribution corrections would need their own finite scope and meaningful fixtures. Native tests could then produce the missing host, lifecycle, failure, enrollment, and package receipts. Successful results would support only the profile actually tested.

A future rollback design should use documented native disable/uninstall controls and the required reload or session transition, tested at the selected host/build. The old `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=0` is not a rollback switch: current documentation says the flag is ignored from 2.1.287. Disabling installed mods is also not equivalent to disabling built-ins or all remaining plugin components. No control was exercised here. [S04 documented controls](https://code.claude.com/docs/en/plugins/mods/overview), [S06 administrative controls](https://code.claude.com/docs/en/plugins/mods/admin).

The report creates no implementation beads. It does not add a registry entry, relax a gate, alter a waiver, install a dependency, dispatch a provider action, or activate a mod. Those boundaries preserve the existing decision process while allowing useful research to progress.
