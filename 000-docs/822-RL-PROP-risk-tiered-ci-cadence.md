# Risk-tiered CI cadence: preserve merge assurance, test preparation improvements

Status: **proposed design; workflow changes require owner approval**. Beads: `claude-y261`. Research baseline: `8faf055b1e6fe652cf6bf2a05aed66d378be122f`, captured October 23, 2026. Filing baseline includes the subsequent research-only record 821. No workflow, branch-protection rule, operator merge policy, secret exception, provider, deployment, scheduled activation or cache has been changed by this proposal.

## Abstract

This repository needs dependable merge assurance while long browser and link checks consume elapsed time. This engineering audit asks how to reduce avoidable CI work without reducing current security coverage. It inventories 40 tracked workflows and 92 static job definitions, then examines seven completed logical runs in a fixed 24-hour window. Independent review verified source captures, operational identities, 113 job records and 1,603 step records. Four Validate cases completed in 280–373 seconds from creation to last job completion; the failing Supabase case remains a failure. Two browser cases took 767 and 2,454 seconds, and one link case took 1,748 seconds. These observations have one case per stratum and establish neither causal savings nor billing. The slow browser case spent substantial time fetching OS dependencies before browser download; the link case restored a cache that its application discarded as stale. The proposal therefore retains existing merge gates and risk routing, adds no replacement by nightly checks, and prioritizes separately approved preparation and freshness experiments. A complete job disposition map, trust constraints, staged measurement protocol and rollback conditions make future changes reviewable. Broad scheduled assurance supplements PR checks; publication and credential-capable jobs retain their existing guards and authorization.

Keywords: continuous integration; merge assurance; trusted routing; cache freshness; browser preparation; operational evidence; risk-tiered cadence.

## Problem and research question

The question is: **How can this repository reduce avoidable CI work and latency while preserving its current required merge contexts and source-risk coverage?** A workflow can consume elapsed time without being redundant. Repeated tests can also protect different revisions, events or privilege transitions. Moving such work to a schedule might make a PR look faster while allowing a faulty artifact or unsafe source change to merge. This proposal first establishes the actual control boundary, then separates evidence-backed observations from design hypotheses.

The captured source contains 40 workflow files, 92 job definitions, and 25 definitions in Validate, including its aggregate. The aggregate has 24 exact dependencies. Runtime matrix expansion produces 27 hosted jobs in the sampled full Validate runs. GitHub registers 43 active workflow entries, including three paths outside the tracked set. These denominators answer different questions. Registry state proves neither that a schedule ran nor that a separate operational hold has been resolved. [Pinned workflow tree](https://github.com/jeremylongshore/tons-of-skills-marketplace/tree/8faf055b1e6fe652cf6bf2a05aed66d378be122f/.github/workflows).

The expected deliverable is a bounded design that a maintainer can review. It does not graduate advisory skill evaluation, adopt a kernel/schema change, release a package, approve a scanner exception, or resolve the separate Nov3 thirty-day CI followup. Finishing this research task would mean the design and evidence are filed, reviewed and merged; implementing its experiments requires a separate owner decision.

## Current merge contract

The captured branch API requires exactly `ci-required`, `gitleaks` and `skill-conform`. The first two bind app ID 15368; conform has a null app binding. This snapshot qualifies repository prose suggesting every required check is explicitly app-pinned. It is not authorization to change the binding. Its check-run failure handling means a passing same-name result need not erase an earlier failing signal. Commit statuses are reduced to the latest context result, so these two signal types must not be conflated.

Two E2E header comments are inconsistent with the executable and operator controls: main pushes have path filters, and observed nonadvisory E2E checks remain part of the operator merge decision despite a comment describing them as nongating. A separately captured five-head, post-window snapshot contains 36–40 required-name union entries per head and 46 distinct names across them. The helper accepts some neutral/skipped outcomes as policy results; neither is proof that a test executed successfully. This proposal preserves the stricter reporting distinction and existing owner review of conditional outcomes. ## Proposed cadence and complete disposition

The proposal uses additive assurance tiers. **PR retains the current applicable contract**; nightly candidates inspect broader deterministic drift and reproducibility; weekly candidates inspect maintenance, long-window trends and expiring evidence; release retains fresh artifact, credential and provenance controls at the publication boundary. A scheduled check never substitutes for required PR validation in this design. Operational issue synchronization, responses, deployment and package publication remain event/manual actions under their existing conditions, rather than becoming scheduled test jobs.

The accompanying complete map covers every workflow/job pair in the 92-definition inventory. Its existing-trigger column records current source; its recommendation column is a proposal, including explicit “no new cadence” decisions. No recommendation activates a provider, external sync, Slack notification, release or deployment. Existing weekly sync source and active registry state do not settle its operational hold. Security rationales explain retained PR or privileged boundaries. The map is a design accounting tool; it is not a claim that all 92 jobs run on every PR or that every job is a branch-required gate.

### Incremental assurance required for additional replays

DA2 identified that a scheduled deterministic replay may add cost without adding evidence. Each of the five C entries therefore has an entry hypothesis, recorded in the data. Actionlint targets a changed runner/toolchain compatibility surface; filesystem and Windows contracts target changed OS/path semantics; validation census targets environment-sensitive interpretation of a fixed corpus; generated-content comparison targets a changed generator runtime producing different bytes from identical inputs. These are supplementary offline fixtures on trusted source, never new source sync or provider operations.

Before implementation, record the changed environment/input identity, distinct expected failure mode, prior evidence it is absent, and observation window for useful findings. If source, toolchain and relevant environment are unchanged, default to **omitting the replay** unless a specific reproducibility risk justifies it. Measure incremental unique findings and setup cost; reject low-yield additions instead of treating a nightly run count as assurance. Current PR checks remain required regardless of whether any additional replay is approved. The separate full-matrix/integration schedule remains a future measurement decision: this evidence does not justify moving it away from current PR execution.

## Experiments to consider after owner approval

**Preparation first.** Compare unchanged hosted E2E with a digest-pinned official Playwright image matching the exact project Playwright version. Keep the Node floor, lockfile, browser projects, build stages, test selection, accessibility checks and evidence uploads identical. Check container user, filesystem/network behavior and required system libraries against actual tests; image use is not automatically an isolation guarantee. Capture image provenance and update policy. A rollback restores the prior hosted setup, not a weaker browser list. This is a candidate experiment, not a tested image or implemented remedy. [Playwright Docker](https://playwright.dev/docs/docker).

**Dependency caches.** Cache downloaded dependency stores, keyed by OS, architecture, package manager/runtime version, exact lockfile and a cache-schema version. Keep root pnpm and marketplace npm boundaries explicit. Use frozen installation after restore; a cache hit must not bypass package integrity or validation. Restore prefixes must not allow old executable build output to masquerade as a current result. Do not store credentials, private environment files or provider responses. Scope reads and writes by event/branch trust; never consume an untrusted PR artifact in a credential-capable job merely because its name matches. Record both action-level restore and application-level reuse. [GitHub cache reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching).

**Link freshness.** Evaluate a bounded freshness bucket combined with checker/config version and relevant input identity. Preserve lychee's maximum-age rule, exclusions, failure policy and complete requested URL population. Record stale-discard counts, actual fetched URLs, errors and retry spans. Do not extend TTL, suppress failures, warm a privileged cache from arbitrary PR code or run a destructive cache cleanup to improve a chart. A fresh full comparison is needed because a restored but discarded cache proves neither safety nor effective reuse. Future cache behavior must be measured alongside freshness, not against action-hit percentage alone.

**Browser binaries.** Do not make binary caching the default response to the observed OS-package delay. Playwright's CI guidance discourages browser caching and states that Linux system dependencies are not cached. If a separately approved experiment nevertheless tests it, bind the cache to the exact Playwright/browser version and preserve OS provisioning. Installation and test behavior must still match. Restoring binaries cannot be counted as evidence that apt preparation was avoided. [Playwright CI](https://playwright.dev/docs/ci#caching-browsers).

**Sharding.** Only after preparation measurements, compare the existing browser workload with two balanced shards on the same tree, OS/image, projects, test discovery and options. Preserve complete test-ID coverage across shards, explicit conditional skips and aggregate failure behavior. A missing, cancelled or failed shard fails the experiment's candidate assurance. Include setup duplication, artifact merge and total executed-job spans when evaluating benefit; lower latency can cost more total resources. Keep independent jobs out of `ci-required` until their control design has explicit approval. [Playwright sharding](https://playwright.dev/docs/test-sharding).

**Local preflight.** Before publication, run relevant existing deterministic checks, registered commit-scope validation and narrow changed-surface tests. Reuse repository commands and source ownership instead of writing a competing validator. Record exit status and source identity; a formatter changing a file requires renewed review. Local preflight can catch mistakes before hosted checks, but local output is not a substitute for hosted required contexts. It must neither load provider credentials nor silently run optional live evaluation. Any automation of these proposals requires its own reviewed implementation.

## Measurement, graduation and rollback

For each candidate, propose at least five matched baseline/candidate pairs per affected risk stratum, split across at least two UTC days; this is an engineering entry criterion, not a statistical guarantee. Use the same tree, exact head/base/integration identity, dependency versions, test set, runner class and relevant event semantics. Randomize or alternate order where feasible and retain failed, retried, cancelled and unavailable observations. A forced-full run may be useful only when it has the same meaningful inputs and authorized event context. Do not pool unrelated workflow families or count carried attempt results as newly executed tests.

Capture job/step start and finish, initial waits, setup/package transfer, effective cache state, test duration, total elapsed spans, all conclusions and artifact identities. Report per-stratum sample size, medians and ranges after sufficient measurements. Distinguish critical-path latency from summed job spans and cost; billing needs its own authorized source. Set a predeclared candidate target, for example a 15% median latency improvement without more than 10% growth in summed job spans, while treating security and coverage equivalence as mandatory. These are proposed decision thresholds, **not achieved results**. A missed performance target can reject an optimization even if its tests pass.

Before graduation, exercise malformed or incomplete routing evidence, changed executable mode, mixed paths, dependencies, renamed or deleted files, unknown event, cancelled shard, stale cache, untrusted artifact and missing check cases in a separate implementation review. Expected unsafe or uncertain cases choose full validation or fail closed. Verify the exact three branch contexts, separate conform workflow, aggregate dependency/skip sets, scanner fixture controls and publication preflight stay intact. No failed known security control may be accepted because a latency target improved. [GitHub workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax).

### Responsible use and trust boundaries

Any experiment begins as an additional observation with normal required gates still active. No new privileged trigger may check out and execute untrusted PR code, trust arbitrary cache contents or receive unnecessary secrets. Cross-job artifacts require exact source/run/attempt and producer verification plus content hashes; hashes identify bytes but do not alone make an untrusted producer trustworthy. Avoid transferring mutable dependency/build output across the untrusted-to-credential boundary. [GitHub secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use).

Rollback is triggered by any coverage mismatch, integrity or trust failure, missing context, unexpected skip, nondeterministic artifact, error-rate regression, or predeclared performance failure. Stop the candidate through an ordinary reviewed revert of the approved implementation and restore its pinned previous preparation/cadence. Preserve experiment evidence and let genuine active required runs finish; do not cancel them simply because they are slow. Existing gates remain usable throughout. Require fresh normal checks and exact remote verification after rollback. Policy bypass, force-push, credential changes and cache deletion are outside this rollback authorization.

## Decision and remaining uncertainty

Proceed with review of this additive design and its evidence. Prioritize effective cache freshness and version-matched preparation experiments because observed logs make those hypotheses concrete. Preserve every current applicable PR/security/publication boundary. They are explicit inputs to future measurement rather than invented conclusions. The existing Nov3 followup retains its separate window and evidence requirements. Owner approval is required before any workflow implementation; approval of the research report does not approve activation.
